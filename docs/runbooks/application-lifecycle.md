# 应用排空与退出契约

本文件只描述四个应用角色的进程行为、配置兼容和验收条件。域名入口、代理和证书由宿主机独立管理，不在本仓库配置或编排。本轮没有实现生产发布控制器，也没有改变独立 API、Admin、Worker、Scheduler 和一次性 migrate 的拓扑。

## 信号与状态

| 输入 | 应用行为 | 健康状态 |
| --- | --- | --- |
| 正常运行 | 接受本角色工作 | ready 同时检查依赖、基线、运行配置及后台循环 |
| `SIGUSR2` | 进入不可逆 draining；API/Admin 继续处理仍被路由过来的请求；Worker 暂停本实例消费；Scheduler 停止新扫描并关闭节点监控 | ready 503，live 200 |
| `SIGTERM` / `SIGINT` | 执行关闭、结束状态流、等待活动 HTTP 和本地工作，再释放依赖 | HTTP 监听进入关闭，不再承诺健康接口可访问 |
| 退出截止时间到达 | 仍未退出则记录错误并退出 1 | 异常退出，不冒充排空成功 |

`SIGUSR2` 只改变应用就绪状态及后台领取行为，不会自动改变外部路由。对 API/Admin，最终退出的前提是外部入口已经停止向该实例分配新请求。Docker 的 healthy/unhealthy 标志本身不保证这一点。重复 drain 幂等；当前不提供恢复接流量的信号，回退应启动经过兼容检查的实例。

Worker 暂停只影响本进程，不暂停整个共享队列。已开始的处理保留 BullMQ 锁与 PostgreSQL 租约续期；关闭等待这些本地步骤完成。极少数暂停时已经取出、尚未领取 PG 任务的投递可由既有 Outbox 对账补投。远端等待任务以持久状态交接，不要求所有业务任务终态后才能关闭。

当前采用共享队列的轻量发布顺序：先使新 Worker 就绪，再暂停全部旧 Worker 领取；随后更新 Scheduler，最后交接 API。API、Worker、Scheduler 同机成组部署不增加任务归属组，也不要求同一时刻停止整组。旧 API 在过渡期继续受理的任务仍可由新 Worker 执行；新任务类型只能在共享队列所有旧消费者均已停止领取后产生。详细应用契约见 [部署约定](role-deployment.md#worker-优先的应用交接顺序)。

用户侧稳定性为最高优先级。Admin 文档试跑直接调用可访问的解析 API，只在内存保留状态/结果；不创建任务、审计、节点分配和持久回调记录，不接入机器开停、调度或恢复流程。允许发布/重启时中断，关闭时终止本地等待，不要求等所有试跑结束才能发布。管理员鉴权/配置读取、配置写入校验以及用户正式任务的节点占用/资源回收机制继续保留。

## 时间预算

| 角色 | 应用默认截止时间 | Compose 默认宽限期 |
| --- | --- | --- |
| API / Admin / Worker | 300000 ms | 330 s |
| Scheduler | 30000 ms | 60 s |

宿主直接启动进程时使用 `SHUTDOWN_TIMEOUT_MS`，允许 1000–3600000 ms。Compose 按角色使用 `API_SHUTDOWN_TIMEOUT_MS` 等四项映射到该变量，容器宽限期对应 `API_STOP_GRACE_PERIOD` 等四项。修改时必须让容器宽限期大于应用截止时间，并为日志与资源清理留余量。

这些默认值是有限退出预算，不是“所有任务最多五分钟”的业务保证。`HTTP_REQUEST_TIMEOUT_MS` 限制接收请求的时间，并非整个处理函数的截止时间。长上传、供应商调用及多步骤处理应按实际最长本地步骤重新评估。清理完成后保留不维持事件循环的截止计时器，避免遗留句柄让进程永久驻留。

## 排空观测

- `application_draining`：进入排空/关闭后为 1。
- `http_requests_in_flight`：尚未关闭的业务 HTTP 响应，含流，排除健康和指标探针；客户端中断后会归零，不能把它当作业务成功计数。
- `background_operations_in_flight`：Worker 本地处理器或 Scheduler 扫描及监控关闭过程。持久化远端等待不计入。

以上指标复用现有 registry，不新增控制接口或端口。Admin 后台试跑不由这个后台工作指标统计，其临时结果不要求持久化，试跑完成与否不作为用户侧排空条件。正常请求关闭时保留活动响应，随后回收空闲连接；已有 SSE 在最终关闭时结束，客户端须重连并重新读取权威状态；Admin 试跑状态丢失时重新发起。

## 运行配置兼容

运行配置 JSON 的内部 `$schemaVersion` 当前支持整数 1。缺省永远解释为 v1；其他值拒绝读取，ready 返回 503，live 仍返回 200。该元字段不作为 Admin 可编辑字段，也不会在普通保存时自动补入已有记录。

同契约版本只允许新增可选字段。旧读者对未知持久字段不应用、不回显；已知字段仍严格校验类型、范围、跨字段关系及生产限制，存储全量字段继续检查秘密信息。Admin 输入仍严格限制分类和字段。事务保存只合并已验证 patch，保留原始未知字段及版本元数据，沿用 revision CAS 和审计，不把本版默认值写满共享记录。

首次部署此能力时，修复前的旧二进制仍不认识新增字段。先使全部相关消费者具备兼容读取能力，再启用新增可选配置。已知字段语义、类型、安全策略发生不兼容变化时，提升契约并安排明确的升级边界；常规新增兼容字段不增加版本路由或兼容平台。新任务类型通过上述 Worker 优先顺序控制开放时机。

## 解析提交不确定状态

`intent` 表示已准备提交、但本地还未保存远端 jobId。没有可信结果时仍禁止盲重试 POST，不能为了自动恢复而重复调用可能计费的远端服务。

已认证持久回调只有同时匹配请求身份、内容指纹和远端 jobId 才能将相应 intent 收敛为已提交 job。按任务→回调收件箱顺序锁定，保留任务版本、租约和取消标记；原活 Worker 或原 Scheduler 恢复路径继续处理。重复回调不重复产生业务效果，冲突拒绝，旧请求不能覆盖新请求。无可信回调时仍保持待核对，不承诺所有未知提交自动恢复。

取消与已知远端任务提交并发时，同一有效租约持有者可交回执行权并立即再投递，让新 attempt 继续取消；该窄交接不允许旧 attempt 提交结果，不允许 intent、不匹配 owner/attempt 或失效租约交接。

## 尚未覆盖的发布条件

本轮未实现双版本镜像编排、入口切流、旧镜像回滚演练、上传断点续传、Scheduler 错过时间窗补跑或生产迁移策略。Admin 试跑状态持久化已明确不要求，不列入待办或验收阻塞。当前未上线唯一基线规则保持。共享 PG/Redis/存储、密钥稳定性、版本间数据/任务兼容、重叠容量仍需在实际发布前验证。不能把复制整套 Compose 成两个 project 当成共享依赖的应用双实例。

验收与证据见 [应用发布基础加固](../acceptance/release-hardening.md)。

后续同机真实容器分角色切换及回切已演练；历史跨版本发布仍因初始化基线校验值不同而阻断，这不等同于业务结构必然不兼容。结果见[容器演练](../acceptance/release-rehearsal.md)。当前同机部署组与共享队列方案见[部署契约](role-deployment.md)及[轻量发布验收](../acceptance/worker-first-release.md)。
