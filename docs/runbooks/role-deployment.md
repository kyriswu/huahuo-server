# 统一代码与按角色部署

最新确认的主方案：API、Worker、Scheduler 同机成组部署，水平扩展时增加这样的部署组，Admin 可独立部署。各组继续共用持久任务和队列；任务不绑定接收请求的 API、宿主机或发布版本。采用 Worker 优先更新的顺序，不新增组标识、组内队列、跨组任务搬迁或自动版本路由。服务地址配置见 [service-addresses.md](service-addresses.md)。

四个角色的代码继续放在同一仓库，共用镜像、公共类型和领域事务。角色入口保留独立，不要求一个角色独占一台服务器；当前按上述部署组组织，不因为部署或扩容拆仓库、拆数据库或将角色合并为一个容器。此前讨论过任务按组隔离，用户随后选择共享队列加发布顺序的轻量方案，以此段为准。

稳定性优先级：首先保证用户侧 API、上传、已受理任务及回调的服务与数据一致性。Admin 文档试跑只保留“运行配置 → 解析与模型”中的现有入口，直接调用已配置且可访问的解析 API；请求、状态和结果只在内存中，不写任务、审计、节点分配或持久回调表，不进入用户任务调度或机器开停流程。允许发布、重启或访问另一实例时中断并重新发起，不增加持久化、跨实例接续或强制实例亲和，不以试跑连续性阻塞发布/扩容。现有管理员鉴权、配置读取与用户正式任务的保护机制继续保留。

## 应用启动契约

同一构建镜像可以执行下列任一入口；一个容器只运行一个角色。API、Worker、Scheduler 成组部署仍允许在更新时按角色分步交接，Admin 不受该组发布时机约束。

| 角色 | 容器内启动入口 | 独立运行边界 |
| --- | --- | --- |
| API | `node dist/entrypoints/api-server.js` | 对外业务请求、上传下载、认证回调；不装载 Admin 路由 |
| Admin | `node dist/entrypoints/admin.js` | 管理身份、会话和管理 API；不要求 API 容器在同机 |
| Worker | `node dist/entrypoints/worker.js` | 从共享队列消费，由 PG 租约及版本控制业务效果 |
| Scheduler | `node dist/entrypoints/scheduler.js` | 扫描持久任务、生成时间窗、投递 Outbox、节点监控 |
| migrate | `node dist/entrypoints/migrate.js` | 发布时单独运行的一次性步骤，不随每个业务副本启动 |

`SERVICE_ROLE` 必须与入口一致。每个实例单独启动、检查 ready、排空和退出；实例身份在进程启动时生成。发布控制不能把“替换整份 Compose”当成某个角色的独立更新。

当前根 Compose 仍是唯一服务拓扑；其本地依赖、网络别名和固定宿主端口用于现有部署，并不代表已经支持自动跨机编排。不能在每台服务器各起一套默认 PG/Redis/文件卷，误认为它们共享数据。同一宿主增加副本也须解决端口冲突；跨机应用配置须指向可达的共享依赖地址。

## Worker 优先的应用交接顺序

常规更新以数据库和任务载荷向后兼容为前提；新 Worker 能执行旧 API 已经受理的任务，不要求为每次更新建立一套版本兼容平台。

1. 先启动新 Worker 并确认就绪，再让共享队列中所有旧 Worker 停止领取任务。旧 Worker 保持已有本地工作的租约并完成当前步骤，未领取任务留在共享队列，由新 Worker 执行。
2. 然后更新 Scheduler。正常停止旧实例的扫描并等待当前扫描收尾，再启动新实例；期间已受理任务和 Outbox 保留在 PG，投递可能短暂延后，不依赖某台旧机器继续存活。
3. 最后启动并检查新 API，由外部入口交接请求；旧 API 完成仍到达本实例的请求后退出。即使请求仍短暂落到旧 API，它产生的旧格式任务也已由新 Worker 接收。入口配置及操作由宿主机独立维护，不属于本仓库。

多服务器时，第 1 步针对共享队列的全部旧消费者。不能在某台机器完成全套更新后就启用新任务类型，同时留下另一台机器的旧 Worker 继续领取任务。无需等待整个队列清空或全部远端任务终态，旧 Worker 只需完成持有租约的本地步骤。若未发现消费端变化，仍沿用同一顺序以减少发布分支。

这里的成组部署表示放置方式，不表示同一时刻停止整组。分角色重叠减少同时运行两整套容器的内存和连接开销；具体资源余量仍以目标机器为准。现有排空信号、有限退出、租约及 Outbox 已支持该应用交接，不增加发布控制器。对应验证见 [轻量发布验收](../acceptance/worker-first-release.md)。

## 跨实例必须一致的状态

- PostgreSQL：业务数据、会话、运行配置、回调收件箱、任务和 Outbox；各角色继续使用各自最小权限账号。一个发布步骤管理同一数据库的 Schema，业务副本不自行迁移。
- Redis：处理同一队列的 API/Worker/Scheduler 必须使用相同队列实例及命名空间。各机器自己的 Redis、相同 DB 号或相同 key 前缀不构成共享。网络分区下无法确认的外部结果继续保守核对。
- 文件：跨服务器使用可被所有需要的实例访问的对象存储，已有 OSS/S3 适配器提供基础。`STORAGE_DRIVER=local` 与单机 `user_files` 卷不能作为跨机共享文件的方案；驱动、Bucket、前缀切换需要独立数据搬迁与验收。
- 身份和能力令牌：API 副本使用兼容的 JWT 验证/签名配置；所有相关实例保持上传、播放、幂等密文及回调密钥兼容；Admin 副本保持 Session 密钥一致。扩容不重新生成既有密钥，密钥轮换单独发布。
- 运行配置和任务协议：同契约版本新增可选配置可兼容读取；新 Worker 继续支持已受理的任务载荷。生产新任务类型前，先完成全部旧 Worker 停止领取的步骤，不新增按版本挑选消费者的机制。

## 仍需补齐和验证的边界

1. API 和 Worker 的跨机文件读写须使用真实对象存储验证。本机共享卷的切换测试不证明跨机通过。
2. Admin 普通会话在 PG，文档试跑状态/结果保持进程内存且有界。试跑不保证跨重启或跨副本接续，中断后重新发起属于已接受边界，不要求补持久化，也不作为发布或扩容阻塞项。
3. Scheduler 任务扫描已有 PG 行锁、时间窗唯一约束和 Outbox 租约；多副本并不必然需要新增一个单实例服务，但须验证副本并发与失联接管。节点电源等外部副作用另受 Redis 协调，关闭云功能的测试不证明这些副作用通过。
4. Worker 的并发设置按进程计算；增加实例会增加总执行数、数据库连接及下游调用。已有解析节点全局槽位不等于所有任务的集群总额度。
5. 网络时延、网络分区、跨机时钟偏差、Redis/PG 故障转移以及真实多服务器发布尚未演练。必须按各角色合计连接、CPU、内存和重叠运行预算，不能由单机健康检查推导可无限扩容。

应用排空协议见 [application-lifecycle.md](application-lifecycle.md)，本机容器演练结果见 [release-rehearsal.md](../acceptance/release-rehearsal.md)。域名入口、代理与证书由宿主机独立管理，本文件不配置或编排它们。
