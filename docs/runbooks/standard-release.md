测试发布入口正在迁移到 ACK。当前 `test` 推送只运行 CI，下文保留发布流程和验收约定。发布恢复条件见[测试服务器发布](test-server-release.md)。

当前测试服务器固定部署 `test` 业务代码；test 合并后的 push CI 成功，以 workflow_run 自动进入受保护 main 中的发布流程。普通 test PR 使用 GitHub 原生 Auto-merge；main 仍由 owner 合并。main/test 同步仍走 PR。正式生产尚未接入，其成功基准为未初始化/null；测试基准保留实际成功版本，不因分支调整重置数据库或已应用迁移。自动化应阻断缺配置、历史冲突及验收失败，不能保证任意业务正确。

团队操作步骤见[团队发布](team-releases.md)。GitHub main/test 分支规则、两个 environment 限制和 production owner 审批已保存并回读。main owner 的 PR-only 例外仅针对新增 update 限制，原 PR、strict CI、禁止删除/强推规则继续生效；没有用真实协作者账号做反向实测。首轮手动发布已真实完成，PR #6/#7 已合并并通过 CI，宿主修复已安装核验，本次 test 更新已完成五阶段发布验收，具体状态见[手动发布验收](../acceptance/manual-release.md)。已有 production environment 配置不代表正式生产已接入。

## 准备阶段需要判断什么

从目标**实际成功部署 SHA**到候选整理累计变更。main 的最新提交不必然等于已部署版本。没有目标记录时先查证；失败发布留下的部分 SQL 或容器变化也要纳入判断。

| 领域 | 本期应核对的内容 | 处理原则 |
| --- | --- | --- |
| 数据库 | 字段、索引、约束、角色权限、必要配置记录；代码是否开始使用这些对象 | 冻结已执行 SQL，用新编号；迁移前只读校验，迁移后检查真实对象及权限 |
| 数据修正 | 行数与增长、索引计划、锁/事务时间、并发写入、可恢复性 | 小且可控可随迁移；大或不确定通常独立；根据证据提出建议 |
| API 与 App | 请求/响应、认证、旧客户端、服务之间接口 | 用真实客户端契约和代表性测试确认，不只看类型通过 |
| 队列与异步处理 | 旧 API 已投递任务、新旧消费者、回调、幂等、续租、超时 | 验证载荷兼容及交接；继续采用共享队列和已有 Worker/Scheduler 机制 |
| 配置 | 默认值、必填值、Compose 注入、读取角色、配置记录 | 示例、注入和应用校验同步；真实值提前准备，使用同一快照直到发布结束 |
| 外部依赖与资源 | 依赖地址/版本/权限、限额、存储读写格式、网络与可用容量 | 先验证必要前置条件；新基础设施不隐含为应用发布时自动创建 |
| 运行与恢复 | 重叠期间资源、退出预算、已提交迁移、旧镜像/旧配置可用性 | 健康和选定冒烟通过才记成功；恢复应用不撤销数据库迁移 |

这张表用于发现遗漏，不要求每次建立所有检查。无影响的项目可以说明“无变化”；有疑问先调查，必要时与用户讨论，不把判断强行压成无依据的通过项。

测试 Action 由准确 test push CI 的 workflow_run 触发，主流程来自受保护 main；手动 dispatch 保留作恢复入口。调用器、依赖和 Compose 固定为该 main 控制 SHA；业务、发布清单和镜像固定为已通过同 SHA push CI 的 test 头。调用前再次核对两头未移动，宿主锁内及迁移前再次检查，变化则拒绝。原 environment、云身份及固定测试实例不变。

## 数据变化的选择

**随发布执行**适合已知范围的小修正、启动所需配置记录或已证明能在预算内完成的回填。准备时给出范围/行数估计、查询和索引依据、锁影响、执行时间、失败回滚或重跑方式。没有统一的“小于多少行就安全”规则。

**独立作业**适合大表、持续产生新数据、长时间外部同步或时长不确定的回填。说明游标/批次、限流、幂等、进度、暂停/续跑、对账与完成标准，再单独授权和执行；发布清单可以引用方案，但不自动启动该作业。

双写是一种常用选择：先上线兼容代码和新结构，单独同步历史数据，核对新旧一致性，后续版本切读，旧版退出恢复范围后再清理。双写失败时的原子性/补偿、并发回填的覆盖规则、如何判定同步完成都要审查。小变更也可选择更直接的方式。Skill 应给建议和取舍，不能把这套顺序变成无条件要求。

## 一份候选清单

固定文件 `scripts/release/plan.json`，每期修改；Git 保存历史。采用 JSON 是为了不引入 YAML 解析依赖。此清单不包含真实配置值或任意 shell 字符串。

| 字段 | 约定 |
| --- | --- |
| `id` / `baseRevision` | 发布编号 / 目标实际成功部署的完整 SHA；宿主在发布锁内再次核对 |
| `services` | 本次实际更新的角色，1–4个；未列出的角色保留成功镜像、配置和容器。共享变更列全受影响角色；新增SQL迁移暂仍要求四角色 |
| `database.migrations` | 相对基准新增 SQL 的完整文件名清单；没有变化填 `[]` |
| `database.verifySql` | 本期 `scripts/release/changes/<id>/verify-db.sql`；有 SQL 或数据库代码变化必须提供 |
| `database.dataChange` | `none`、`inline` 或 `separate`；后两种必须说明理由 |
| `configuration` | `reuse` 或 `candidate`；变更键、角色、是否必填/有默认值和已审配置文件，无真实值 |
| `dependencies` | 必要外部依赖及本期 `verify-external.mjs`；同一文件只运行一次 |
| `backfill` | 独立作业的文档引用；只记录，不执行 |
| `compatibility` | 已审数据库/API/任务/配置兼容判断；有一项未满足则不能走自动更新路径，先讨论方案 |
| `smoke` | `health` 或 `authenticated`；健康模式只用于明确接受该边界的测试环境，生产必须认证冒烟 |

默认值足够、无需改变实际配置的新增变量可使用 `reuse`。代码已经停止读取、清单标记 `operation:remove` 且 `required:false` 的旧键也可复用成功配置：残留 ENV 值不再生效，无需仅为删掉它们另做候选配置。修改键、删除仍标记必需的键或新增无默认值的键使用 `candidate`，提前在目标环境准备。两种模式都保留 `reviewedFiles` 审查门禁，不能只靠声明推定旧键已停用。

候选快照通过后原样用于迁移、验证和容器，不中途重新读取另一份 ENV。所有角色与迁移账号必须指向同一个目标库，比较时不输出凭据。

CI 使用 `pnpm release:review` 校验干净的真实提交、基准祖先关系、累计差异、已执行迁移不得修改/删除、新迁移与清单一致、数据库验收文件和配置审查范围。兼容项必须是布尔值，存在 false 时仍可完成代码测试，输出 `automaticReleaseReady:false`；这不授权部署。`pnpm release:check` 保持严格，仍拒绝任何不兼容项。校验不能靠文件名识别每一处隐藏 SQL 或配置读取；准备阶段仍必须审查真实业务代码。

## PR 上线清单与 ENV 值校验

最终 PR 使用仓库模板，写清主要功能、改动范围、冲突及解决方式，以及上线前人工项；没有冲突或人工项也明确写无。ENV 逐键列操作、容器、默认/必填、目标要求、准备位置/时点、完成状态和验收方式，不包含秘密值。

`configuration.verifyFile` 可指向 `scripts/release/changes/<id>/verify-config.mjs`；有 `operation:change` 时必须提供。CI 核对声明及文件；发布的 config 阶段在五个实际角色容器中执行同一脚本，用 `SERVICE_ROLE` 分支。脚本只做本地 ENV 断言，5 秒上限、输出受限且不转发，任何失败停止在写库前。新增必填项仍有通用缺失检查，应用配置解析仍照常运行。需要业务范围/开关联动/目标值检查的新增项也应提供此脚本。

例如非敏感预算修改可检查 `if (process.env.SERVICE_ROLE === 'worker' && process.env.FEATURE_BUDGET !== '20') process.exitCode = 1`；应按本期含义检查合理范围或精确要求，不能只判断字符串非空。秘密不写入脚本，也不提交可猜测的摘要；存在/格式通过不能证明秘密已正确轮换，精确值由授权私密来源核验并记录完成状态。脚本禁止网络、SQL、写配置及付费调用；它是已审代码，不是任意脚本沙箱。配置仍需提前人工准备，校验不会自动生成真实值。

## Migration 与只读验收

`pnpm db:generate descriptive_name` 从当前完整编号生成新文件，不覆盖已有文件。填写 SQL、必要普通索引/权限和兼容说明后去掉草稿标记；草稿不得发布。`0001_initial_schema.sql` 已冻结，新环境从它顺序建立，后续追加 `0002` 等，不对已有库重新执行初始化。

执行器先验证完整文件清单和已应用历史，再进行写入；序号断档、未知历史或 checksum 不一致均失败。每文件一个事务，已有成功文件保留。执行器管理事务，SQL 不自行写 BEGIN/COMMIT/ROLLBACK；不支持事务外的 `CREATE INDEX CONCURRENTLY`。确需这种在线 DDL 时，先安排独立受控维护步骤，再在后续发布验收，而不是伪装成已执行的编号或自动扩大发布能力。

本地开发和测试服务当前共用数据库及云资源。发布不能因此省略迁移阶段：先核对已经执行的编号与 checksum；没有 pending 时明确显示“无需执行”，有 pending 时执行已审清单，任何差异停止。清单仍列出相对实际部署基准新增的 SQL，不能因本地已经应用而删掉编号。本地执行结构变更会立即影响仍运行的测试旧版，须在执行前确认兼容，不等容器更新后再处理。CI 使用独立临时 PG/Redis，不清空共享数据库，也不以演练为由调用真实付费服务。

`MIGRATION_STATEMENT_TIMEOUT_MS` 默认 30 秒、上限 60 秒；`MIGRATION_LOCK_TIMEOUT_MS` 默认 10 秒。超预算先调查锁与方案，不盲目加大超时。部署总超时与单次 SQL 预算不同。迁移失败记录成功编号与失败编号，不输出 SQL 或连接信息。

只读验收文件必须是**一条 SELECT**（可 WITH/UNION），返回 `check_name` 文本和 `ok` 布尔两列，1—200 项、名称不重复、每项都为 true 才通过。例如：

```sql
SELECT 'expected_column' AS check_name, EXISTS (
  SELECT 1 FROM pg_attribute
  WHERE attrelid='public.tasks'::regclass AND attname='resume_count'
    AND atttypid='integer'::regtype AND attnotnull AND NOT attisdropped
) AS ok;
```

它在只读事务、命名 prepared statement 和超时限制下运行，拒绝多条语句；逐角色执行才能发现应用账号权限缺项。通用检查始终验证迁移全部完成和物理外键数量为 0。本期按实际变更增加类型、索引有效性、约束、权限、必要配置和有限数据断言，不扫描全量敏感业务内容。SQL 仍须审查，这不是对任意不可信 SQL 的沙箱。

## 固定执行顺序

仓库维护计划、应用镜像内的 `release-gate`、迁移器、冒烟与 CI；宿主维护部署和入口切换。宿主实现独立于仓库，下面是接口顺序，不包含入口配置。

1. **预检（含构建、配置）**：核对目标、发布锁、当前成功 SHA 与计划基准，以及控制代码与业务候选来源；获取候选提交、构建不可变镜像；确定配置快照。五角色 `release-gate config`，`migrate` 角色 `db-preflight`，必要的 `external` 检查。认证冒烟所需凭据要在写库前准备并验证。
2. **迁移**：一次性 `migrate` 服务运行现有 `dist/entrypoints/migrate.js`；显式 `--no-deps`，不隐式启动或替换业务容器。无待执行项时返回空清单并显示“无需执行”，仍保留本阶段的校验结果。
3. **迁移验收**：五角色执行 `release-gate db-verify`；四运行角色执行 `release-gate runtime`。候选的完整 schema/runtime settings 检查放在迁移后，避免先要求一个尚未创建的字段。
4. **容器切换退出**：只更新清单`services`中的角色，顺序仍为Worker、Scheduler、API、Admin；API未列出时不进行API切流。候选健康通过才接流；旧服务使用下述数据库排空预算。Admin 试跑允许中断，不增加持久化或恢复机制。
5. **冒烟清理**：运行清单指定的验收。认证模式调用已有固定六次 GET，缺少/过期凭据必须失败。通过后才清理未使用旧应用镜像，保留当前与上一个成功版，并记录实际 SHA、镜像、配置摘要、迁移编号、验收范围和是否发生强制退出。

以上五阶段从进入远端发布开始。此前的 checkout、源分支、CI 或 OIDC 校验失败由 Actions 对应步骤显示，此时远端发布未开始，不生成虚假的 N/5 进度。收到远端阶段记录后，失败显示“已完成 N/5”、当前失败阶段及未执行阶段，不能把尚未执行的步骤标为通过。如果旧协议或本次调用只提供终态结果，只报告“终态复核”及能够证明的状态，不据此伪造五步执行过程。

外部检查只能是已审仓库内本期文件，整批最多 20 秒、输出受限并不转发原始异常；检查内容要只读且有界，不调用真实付费业务。它只能证明所检查的前置条件，不能推导所有后续业务正确。

## 排空预算与退出结果

数据库配置 `deployment.drainTimeoutMs` 默认 `600000` 毫秒（10 分钟），允许 10—60 分钟。本次新增迁移只在该键缺失时写入默认值，不覆盖已有配置。服务收到首次排空信号后固定本次预算，重复停止信号或随后修改配置不延长已开始的排空。宿主使用预检时读取的本次发布预算；发布期间不要调整该项。发现配置变化或提前异常退出时停止发布并核查，不将其当作正常排空。工作提前完成就立即退出；达到预算仍未完成则强制结束。Compose 的 `stop_grace_period:3630s` 只是覆盖配置上限的保护值，实际排空按数据库预算执行，不能将它理解为每次固定等待一小时。

应用用退出码 `124` 标识排空超时。正常完成与到期强退必须分别记录：`forcedRetirements` 记录本次强退情况；其他部署检查通过后，存在到期强退的结果使用 `OK_WITH_FORCED_DRAIN`，调用方显示明确警告。这表示服务更新完成，但旧工作并非全部自然完成，不能声称无损排空。提前失败、异常退出等仍应使发布失败，不能仅凭退出码将它们归为正常到期。

时间预算必须在写库前核对。本轮候选 Action 上限 100 分钟，STS 会话、保存命令和调用器上限均为 90 分钟，调用器最多轮询 1080 次；宿主全程上限 5300 秒。预检要求剩余时间足以容纳六次退出预算加 600 秒预留，不足则在写库前拒绝，不偷偷缩短数据库配置的预算。应用允许设置 60 分钟不代表当前单机发布链路能容纳该值；应先调整发布安排及已授权的总预算，再执行。

以上规则不能追溯改变旧镜像。首次升级时，旧版本固有的 5 分钟/30 秒退出行为不会被新增数据库键改变；应分别记录旧镜像交接结果和新版行为。宿主入口及云端超时的接入状态、实际发布结果分别见[测试服务器接口](test-server-release.md)与[验收记录](../acceptance/standard-release.md)。

## 演练、失败和恢复

```bash
pnpm typecheck
pnpm lint
pnpm build
pnpm test
pnpm test:integration
# 候选提交并且工作区干净后：
pnpm release:review
# 普通自动部署前，额外要求兼容项全部通过：
pnpm release:check
```

集成运行器只创建自有临时 PG/Redis，无生产配置。先从计划中实际基准 SQL 建库，执行候选增量、迁移后断言、逐账号权限检查和重复迁移，再跑业务集成。这覆盖真实升级路径及新旧所需迁移记录的兼容，不自动代表旧二进制业务、大表锁耗时、真实外部依赖或多机切换通过。相应变化要增加代表性数据/旧版行为演练，并在 PR 标明范围。

| 失败位置 | 已发生的状态与处理 |
| --- | --- |
| 预检 | 不执行本次迁移、不替换容器；修清单/配置/前置条件后再运行 |
| 迁移 | 本文件回滚，前面已提交文件保留；检查实际迁移记录后继续或提交新修正，不改历史 checksum |
| 迁移后验收 | 旧容器继续服务，保留已提交变更；修复失败断言所对应的问题 |
| 更新或冒烟 | 可能已部分更新/切流，必须查实际状态；保留上次成功记录及本次证据，不能盲删临时容器 |
| Action/本地超时 | 远端可能仍运行；先查已有调用和发布锁，不能直接重复提交 |

默认提交修复代码向前发布，不新增自动回滚入口。确需历史版本恢复时另行明确手动维护，先确认当前库与任务载荷兼容；**不运行旧迁移器、不撤销数据库迁移**。清理只针对不再使用的本项目镜像和容器，不清用户数据卷或其他项目。

## 发布顺序、重复执行与按角色更新

继续复用同一环境的发布锁和`current.json`成功记录，不引入发布平台或新数据库表。测试执行器已在2026-11-17安装以下保护，真实验证见[验收](../acceptance/release-order-and-services.md)。正式生产尚未接入，不把测试机安装结果推广为生产已启用。

- 普通候选必须是环境最后成功SHA的后续提交。宿主补齐Git历史再检查祖先关系；缺历史或版本倒退就拒绝，不通过比较时间或SHA字符串大小决定顺序。已有准确分支头、同SHA CI和清单基准校验保留。写库前、换容器前再次确认成功记录未变化。
- 同SHA重复执行不重新迁移、构建或换容器。按每个角色自己的成功镜像ID、镜像默认ENV与保存的服务ENV检查实际容器，再验证健康；镜像/配置漂移、不健康或半更新均不能报“已发布”。若候选配置源已改变，也不能用重跑旧SHA应用它，应准备新的发布提交。
- `services`明确指定实际更新范围，不根据文件名或整个共用镜像的变化自动猜测。例如仅Admin改变可以声明`"services":["admin"]`；API路由改变通常列API；共享服务、任务载荷或公共配置改变时，审核者列出所有受影响角色。不能为了少重启漏掉依赖方。
- 未更新角色复用成功快照中的完整服务定义，保留旧镜像和ENV，不调用其重建、停止或桥接流程。开始前验证这些角色没有漂移；选中的角色允许由新代码修复此前未成功的部分更新，未选角色存在异常则先处理或纳入本期范围。最终仍核对全部四角色的实际结果。
- 生效的配置变更所声明角色必须包含在`services`中，migrate除外；已停用、非必需旧键的删除不强制重启其他角色。迁移仍是独立一次性步骤，没有pending只核对，不重建常驻服务。存在新增SQL时暂沿用四角色更新，因为现有旧镜像会拒绝未知迁移历史，不能通过放宽历史检查获得部分发布。
- 新成功记录增加`updatedRoles`和`roleImages`，逐角色保存不可变镜像身份；没有数据库迁移。成功记录必须提供四角色的 `roleImages`；缺少该字段时拒绝，不从旧顶层镜像字段推断。全局SHA表示最近一次成功发布，不表示未更新角色也运行该SHA。当前和上一成功版本的各角色镜像都保留。

更改角色选择、公共配置或修复业务时使用新提交；不增加强制旧版本覆盖、忽略检查或自动回滚参数。宿主执行器和私密配置独立维护，仓库只维护无副作用的`deployment-policy.py`及校验契约，不收录宿主入口配置。

## 当前边界

常规发布不会调用首次切换的独立维护脚本，也不会再次安装入口或重做首次数据处理。固定云命令只调用常规宿主执行器；首次维护记录和脚本保留为历史证据。每次发布仍保留迁移阶段，先核对已有编号和 checksum，再仅执行清单中的待执行增量。没有 pending 时不执行历史 SQL、不重建业务表；有历史差异则停止。本期真实短信版本没有新增迁移。

## 候选审查与自动部署资格

CI审查与自动部署资格分开。`release:review`允许完整审查不兼容候选并运行测试，历史SQL、基准、配置清单和干净工作区约束不放宽。`release:check`默认仍严格拒绝不兼容候选。只读`release-gate`的config/db-preflight/db-verify/runtime/external模式也可检查不兼容候选，结果明确携带`automaticReleaseReady`；这些命令不执行迁移或替换运行角色，检查通过不能当成发布许可。

受保护main的自动入口先验证准确test push CI、PR与完整变更列表，再只读获取该准确SHA的发布清单。兼容项有false时返回“本项目发布前置条件未完成”，不请求云凭据、不调用宿主命令；普通手动恢复入口也拒绝不兼容清单。宿主自动执行器仍在写库和更换容器之前要求兼容项全部为true。未知、缺失、畸形或无法读取的清单失败关闭，不把它当成无需发布。

首次不兼容升级通过独立受审的维护安排落实，不能为获得CI或自动发布而将false改成true。完成后应保存真实部署SHA、镜像、配置快照及所需成功记录，后续清单以新实际成功基准开始，恢复普通自动流程。宿主实施与恢复操作留在仓库外。本仓控制变更需按团队流程先由owner审核合入main，再同步test；本地修改不代表GitHub自动入口或宿主已更新。


发布范围由本仓清单决定，当前为api-server/admin/worker/scheduler及一次性migrate。候选审查与自动发布资格的区别只针对本项目；它不是跨项目协调器。Server成功记录只记录Server，回退也只处理Server。其他项目的接入与发布按各自流程执行。
