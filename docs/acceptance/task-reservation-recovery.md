# 任务基础机制与预留恢复（2026-11-17）

修复P1/P2复核的第4项，并按用户最后确认只加强任务基础机制；第3项检索问题暂缓。额度模式尚未确定，本轮不推进计价、扣费模型或结算规则。账本唯一索引和自动成功扣款的新增方案已撤回，保留上一轮必要的预留释放修复及既有示例行为。

## 实现与边界

`tasks/lifecycle.ts`统一终态状态、版本、租约和事件，独立于扣费规则；数据库内业务收尾通过一个可选事务函数接入。`tasks/reservations.ts`仅承接已有预留释放适配，`billing/reservations.ts`保留上一轮唯一的释放实现。Scheduler恢复耗尽任务、Worker最终失败、排队取消、文本更新替换旧任务及解析服务确认取消均在已有任务事务内调用。任务、attempt、预留、批次余额、release账本与事件要么一起提交，要么一起回滚。成功结算仍沿用此前已配置的BillingService行为，未新增准入、计价或自动扣款规则。

Scheduler改为逐任务短事务恢复与独立Outbox修复，已恢复任务先提交并释放锁；单个任务的一致性错误回滚并报告，其他恢复、修复和派单继续。每轮最多50条，基于updated_at/id轮转，完整保留数据库时间精度；即使整页任务异常，也不会挡住后面的任务。扫描游标只有两个进程内字段，重启丢弃无损，实际状态仍在PG。连接等基础设施错误继续使扫描报错，已提交任务不回滚。多实例沿用行锁、SKIP LOCKED和版本保护。

Worker领取、续租和收尾使用数据库实时时钟；持有行锁后重新确认版本、owner、attempt及租约。等待锁后已过期的心跳不能复活租约，迟到的成功/失败写入、外部提交意图及远端回执交接都不能绕过保护。恢复异常通过结构化任务ID/错误码日志及低基数task_recovery_failures_total暴露，沿用现有Prometheus抓取，无新进程或追踪框架。

任务和预留归属必须一致；分配金额总和、批次所属用户和可释放余额也校验。预留行锁与released状态保证重复恢复、并发调度和释放重放只归还一次。没有预留的任务沿用既有流程；已存在预留的释放不依赖当前BILLING_MODE或是否注入BillingService。

自动重试及仍有可用执行次数的恢复保留原预留。外部unknown/submitted及受管理的在途解析/启动进入reconciling，预留即使过期也不在这里释放。解析的外部结果已确认、取消正式落库后才释放。

现有demo手动重试先校验次数，再按旧预留金额创建新预留，与任务重排队同事务；幂等重放不重复预留，余额不足全部回滚。Admin仍保持财务只读：无预留任务的管理重试不变，有预留任务不能从该入口绕过资金准入，返回BILLING_NOT_CONFIGURED。此轮不增加Admin财务写权限或新的跨服务调用。
