# SSE 代理短时基准（2026-11-16）

结论：500 条并发 HTTP/1.1 SSE 下，Nginx 与 Traefik 单层代理均维持 1000 条 ESTABLISHED TCP；双层代理各自维持 1000 条。Traefik 在此协议下没有减少连接数。本轮未验证 Docker 自动发现，不能将动态路由便利与连接资源优化混为一谈。

## 环境与方法

本机 Colima Docker 29.5.2，虚拟机 2 CPU / 1.914 GiB RAM，与已有开发服务共享资源。独立网络及四个临时容器，未修改现有业务容器。Node 26.12.1、Nginx 1.28、Traefik 3.6.25（镜像 digest sha256:31267173a15b4944e797a76ffd9c419707c8d8b32fe5b610f80cd0cfa05f372d）。

模拟源立即输出首个事件，随后每 100ms 输出一个事件，正文含 200 字节固定文本、序号与时间戳。最终复测每条路径 500 并发、15 秒、单轮；发压端与源处于同一虚拟机的不同容器，使用 HTTP/1.1，无 TLS、认证、数据库、真实 Agent 或模型调用。Nginx 关闭响应缓冲；Traefik 使用 file provider。客户端在截止时主动关闭连接。

首段延迟从发起请求至收到第一个完整 SSE 事件，以客户端单调时钟测量；事件延迟为源时间戳至客户端解析事件的差值，毫秒精度。连接数读取各容器网络命名空间 /proc/net/tcp{,6} 的 ESTABLISHED 行，统计代理两端 socket，不是全链路去重后的 TCP 连接总数。内存是负载中 docker stats 单次采样，包含进程基础开销，非峰值或每连接增量。

## 最终同虚拟机结果

| 路径 | 首段 P95 ms | 事件延迟 P95 ms | Nginx TCP | Traefik TCP | 活跃代理内存 MiB | 建连/记录错误 |
| --- | ---: | ---: | ---: | ---: | --- | --- |
| direct | 88.9 | 2 | 0 | 0 | — | 500/500，0 错误 |
| nginx | 91.2 | 5 | 1000 | 0 | nginx 20.23MiB | 500/500，0 错误 |
| traefik | 138.3 | 4 | 0 | 1000 | traefik 57.48MiB | 500/500，0 错误 |
| nginx-traefik | 102.7 | 4 | 1000 | 1000 | nginx 16.68MiB, traefik 85.25MiB | 500/500，0 错误 |

各路径采样时模拟源均为 500 条活跃 SSE 和 500 条 ESTABLISHED 连接；源指标接口临时产生的额外 socket 不纳入 SSE 数量。每条路径收到了约 7.3 万事件，证明本次窗口中存在持续流式传输；未验证逐流序号连续性、慢客户端背压、长期稳定性或断线恢复。

## 解释与限制

单轮、固定顺序且没有预热，不能据首段或内存数值给 Nginx/Traefik 做性能排名。Traefik 单层的首段 P95 高于双层，进一步说明启动、调度和资源波动影响；不能解释为多一层代理更快。现有虚拟机内存有限，其他容器继续运行，测试不代表线上 16核32GiB 容量。

初轮在 macOS 发压，100/500 并发每路 7 秒；发现主机与虚拟机时钟偏差，事件延迟出现负值，全部跨时钟延迟不采用。初轮双层500并发的连接采样已落在客户端结束后，也不采用该连接样本。最终复测迁移发压端到同一虚拟机并延长窗口至15秒，四条路径采样均确认500活跃流。最初两次环境准备分别因 Colima 不共享 /tmp 绑定路径、Traefik 将默认路径动态文件识别为静态配置而失败；修正为 docker cp 和非默认配置路径后完成。

未测 HTTP/2/h2c、多机、真实域名/Nginx生产配置、发布切流、自动发现或付费执行。若目标是减少回源 TCP，下一步应独立验证 HTTP/2 多路复用及 Agent 实际支持情况。若目标是降低路由维护，可评估 Traefik 自动发现，无须承诺连接数下降。

测试容器、专用网络均已删除；未接入 Docker socket，未读取 App/Agent 秘密，未修改业务、迁移、环境或宿主入口配置。临时代理配置仅在 /tmp 测试目录，未写入仓库。原始最终测量与模拟源/客户端位于忽略目录 `.local/sse-benchmark-20261116/`。无代码改动，未重复运行业务回归。

## 原配置扩大至1000并发（后续复核）

保持2 CPU / 1.914 GiB、相同镜像、协议、事件频率、200字节文本和代理配置。每路发压窗口仍为15秒，从全部请求发起后计时，实际单条连接存活略短于15秒，不是每条都精确维持15秒。未调高Nginx文件描述符限制。

初轮1000请求均收到了HTTP响应，但旧客户端只统计传输错误，未区分HTTP失败；源活跃流仅507使问题暴露。随后仅补充客户端观测（HTTP状态、收到SSE的流数、200响应提前结束计数），再完整复跑四条路径。下表使用复核结果；原始初轮保留在忽略目录，不将opened=1000解释为1000条SSE成功。

| 路径 | 收到SSE / 请求数 | HTTP 500 | 事件延迟 P95 ms | 首段 P95 ms（成功流） | Nginx TCP | Traefik TCP | 活跃代理内存 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| direct | 1000/1000 | 0 | 1 | 1106.0 | 0 | 0 | — |
| nginx | 507/1000 | 493 | 4 | 148.8 | 1014 | 0 | nginx 22.28MiB |
| traefik | 1000/1000 | 0 | 3 | 237.5 | 0 | 2000 | traefik 105.9MiB |
| nginx-traefik | 507/1000 | 493 | 6 | 201.4 | 1014 | 1014 | nginx 17.99MiB, traefik 96.11MiB |

所有路径传输错误计数为0，成功200响应的提前结束计数为0；含Nginx的路径各493个HTTP失败，不能报告“全部成功”。直连和Traefik各约14.6万事件；含Nginx的路径各74022个事件，采样均仅507活跃流。

Nginx日志明确出现 `socket() failed (24: No file descriptors available) while connecting to upstream`；读取主进程及worker的/proc限制，Max open files软上限1024、硬上限524288。原配置虽有worker_connections=8192，但不会自行提高该软上限，HTTP/1.1每条代理SSE需前后端两个socket，故约507条时触及限制。该限制属于测试容器配置，不是Nginx能力上限，也不证明线上宿主入口存在相同限制。Traefik单层1000活跃流对应2000个TCP socket，没有减少连接数。

单轮首段延迟明显波动（本次直连P95约1.1秒，而前轮约136毫秒），在该小型共享虚拟机内不能用于性能排名。含Nginx路径实际承载量较低，延迟/内存也不能与Traefik的1000条直接做等负载比较。

本轮同样没有测长期稳定性、HTTP/2、真实Agent、模型或付费服务。四个测试容器和网络均已清理，已有服务未停止，代理配置与资源限制未调整。复核原始数据位于`.local/sse-benchmark-20261116/results-vm-1000-verified.json`。
