# 通用临时上传与业务认领（2026-11-17，本地候选）

本记录保留此前上传解耦与 0007/0008 的验收事实。后续用户确认的“资源只归用户、文件哈希复用、引用计数及 Note 只存当前正文”已由[新验收](user-resources-and-current-notes.md)补充并替代本文的空间归属/上传入参描述；下列旧测试数量不代表最终发布候选的全仓验收。

## 用户确认的边界

- 客户端只配置业务 API Base URL。统一上传组件申请授权、使用服务端返回的地址直传 OSS、确认元信息；文件字节不经本项目 API 或宿主 Nginx。
- 上传阶段只在 Redis 登记临时文件，不写 PostgreSQL 上传表、资源、预留、业务任务或幂等记录；保留鉴权和归属校验，不读取用户额度汇总或判断剩余空间。临时文件不计用户实际占用，本次不增加异常上传限流或临时上传数量／总量限制。
- 临时有效期最多一天，即首次申请起 24 小时，重试、续签和上传完成均不延长；到期后不能再由业务认领。签名 URL 单次最多 1 小时，响应分别返回 `expiresAt` 和 `retentionExpiresAt`。
- 文件只生成一个系统 UUID：临时上传 ID、返回的 resourceId、OSS 对象 key 的 UUID 及后续图片引用一致。OSS 内部分片 UploadId 是供应商传输凭证，不是第二套业务文件身份。
- 上传入参仅文件名、MIME、大小及归属空间。移除 sourceScene、durationSeconds、distillToDigitalTwin；完成不启动解析、转写、索引或其他业务。
- 客户端另行调用业务 API，传文件 ID；业务真正使用文件时，才由同一事务调用统一 ResourceClaims 校验正式额度、登记文件和引用并增加 used。业务失败时登记和计数一并回滚。

## 实现与安全边界

Redis store 用原子 Lua 保持临时回执、幂等和到期索引一致，不维护临时 pending 字节计数；记录不会因 TTL 先消失而失去清理所需定位。24 小时结束的是使用资格，不是自动 TTL；到期后不能认领，清理所需元信息保留到安全清理完成。物理删除由 Worker 扫描执行，供应商故障时可能延后。每个文件的控制操作与认领、清理共用 PostgreSQL advisory 锁；没有 PostgreSQL 上传过程记录，OSS RPC 不在数据库事务内执行。

客户端只得到 OSS part 1 的 PUT 签名。服务端控制初始化、核对单片大小、Complete 与 Abort；完成后旧 part URL 无法重新创建已删文件。Complete 超时保留未知结果，后续通过 HEAD 的服务端上传标记、大小、类型和对象版本恢复，不把客户端的成功声明当作验证。HEAD 不是文件内容、病毒、真实格式或媒体时长检查。

业务成功提交后立即尽力删除 Redis 临时记录；删除失败不会重复计算占用或影响正式空间判定。到期清理仅查询统一 `resources`，不扫描业务表：发现正式资源就只清 Redis；不存在且到期/取消才先标记禁止认领，然后终止上传、删除精确对象版本、最后清理 Redis 回执及索引。清理失败延迟重试，单个坏记录不阻塞后续批次。没有新增认领任务、上传数据库状态机、文件 Copy 或上传回调。

Worker 的 maintenance 角色每 60 秒至多扫描 10 个记录，启动首轮延迟 5 秒；排空时停止新扫描，等待当前有界控制请求完成后关闭依赖。Scheduler 不再扫描已经移除的 PostgreSQL 上传表。正式资源仍通过原引用检查和 `storage.delete` 任务删除。

## 业务接入

Note 正文图片/附件、RAG 母文件、头像、Text 图片及自有 OSS 文件来源通过相同认领方法处理。临时预览只验证归属并签短期 GET，不触发正式登记。`resources` 保留通用文件信息和用户/空间归属，业务目的留在各自业务模块。

解析服务实际提交时，对已登记且归属/版本匹配的自有文件重新生成短期读取链接，使用登记的真实文件名/MIME。签名变化不改变解析请求的稳定身份，已经提交的解析恢复不重复提交。

## 空间汇总与查询

复用 `users` 的主键查询，新增 `storage_used_bytes`、`storage_reserved_bytes` 两个非负 bigint 字段；不增加通用权益表或新的额度政策。上传申请、完成及临时预览不读取额度汇总、不检查剩余空间，也不预留临时容量。只有业务首次使用文件时才按已有正式额度规则，原子判断 `used + reserved + 本次新认领大小` 并增加 used，不再汇总资源或预留明细。

首次业务认领在同一个 PostgreSQL 事务中写入资源、confirmed 明细、引用并增加 used；业务回滚时全部回滚。同一资源再次认领不重复计数。正式文件通过删除任务确认删除后，才同时释放 confirmed 明细和 used；外部删除失败、租约失效和重复执行不会提前释放或重复减少。删除时还核对当前驱动和 Bucket 与登记位置一致。既有存储预留 API 同事务增减 reserved、确认时转入 used；其基础逻辑与临时上传无关，此次不扩展其规则，也不扩展积分、套餐或结算逻辑。

这些写入按用户行串行，统一先锁用户再锁相关任务/资源；不持有事务等待 OSS。不同用户互不争用同一用户行。额度判断成本不再随该用户的文件数增长，但没有以此承诺单用户无限写入吞吐。

资源按 ID 命中主键、按用户/空间/创建时间使用现有联合索引；认领批量查 ID。新增 `resource_refs_owner` 支持业务引用定位，`storage_reservations_active_user` 用于按用户查看有效占用明细及对账，不属于上传准入路径。不提前分库分表、分区或增加缓存；千万行的实际延迟仍需在真实数据分布下验证。

## 明确限制

- Redis 灾难性清空会丢失未认领文件及清理索引，需要按 OSS 清单对账；不会因此删除已登记资源。现有 Redis 持久化/no-eviction 要求继续保留。
- 业务提交后 Redis 暂时不可用，可能留下待清理回执；它不计正式用量，不影响正式空间判定。PostgreSQL 与 Redis 并非原子提交；后续清理仍须先查 `resources`，不能凭 Redis 回执到期删除已登记对象。
- OSS Abort 不保证正在上传的分片即时物理消失，初始化响应丢失也可能留下未知上传 ID。供应商未完成分片生命周期是必要兜底，真实配置尚未检查。本项目不自动覆盖 Bucket 生命周期；不能对通用已完成对象前缀设置 24 小时删除规则，否则会影响正式资源。
- 未完成真实 OSS 联调、千万行资源库压测或 App 上传组件开发。App 只读核对，未修改；未提交、发布、重启既有服务或迁移共享数据库。
