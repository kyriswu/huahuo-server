## 保留的失败与调整

- 最初在 2 CPU、约 2 GiB Docker VM 上叠加多角色副本，并给测试应用 256 MiB 上限，测试 API 出现 OOM/137；提高单容器预算后，多角色同时重叠仍未稳定通过。不能由最终分角色成功推导整套服务双份并行容量足够。
- 提前停止旧 Admin 后，仍有旧连接访问原地址，管理查询出现 404。最终轮改为按角色独立交接，并保留旧管理实例直至该角色切换完成。
- 采用 1500 ms 测试租约并在同机启动其他进程时，原任务租约失效后被恢复排队；最终轮使用实际默认 15000 ms。默认租约也不代表可忽略跨机时延和失联测试。
- 人工协调让慢上传等待超过接收时限，出现 408；最终轮确认上传跨切换并在接收时限内结束。没有扩大生产超时来掩盖这一失败。
- 初始测试设施还有端口未发布、入口启动/收尾、fixture SQL 参数及错误指标监听地址等错误，修正后再运行；各轮报告保留。最终指标从专用监听读取，业务端口不新增 `/metrics`。

因此发布时必须先确认目标实例兼容，再停止向旧实例分配新请求，最后等待旧实例排空。健康状态不会自行完成路由切换，当前仓库仍没有自动发布控制器。

## 后续验收边界

当前历史基线不匹配，不能承诺该历史版本与当前版本直接并存或随时回滚；尚未选择、执行生产 Schema 升级方案。依旧遵守未上线唯一初始化基线规则，不修改旧镜像校验文件、不更新真实数据库 checksum 来使演练通过。
