## 一、技术栈及默认工程选择

### 用户指定，不得擅自替换
- API 框架：Fastify，不换 Express、NestJS、Django 或其他框架。
- 数据库：PostgreSQL。默认本地 Docker 容器，连接参数可以替换为兼容的云 PostgreSQL。不是声称任意“兼容数据库”或整个数据迁移只需换 URL。
- Redis：默认本地 Docker 容器，用于缓存、短期控制数据，并作为所选 BullMQ 队列的后端。

### 本方案补齐的默认实现选择
- Node.js 24 LTS、TypeScript strict、ESM、pnpm。执行时核查仍受支持且与依赖兼容，锁定具体稳定版本；不得使用 latest 浮动容器标签、RC、beta 或无锁安装。
- Fastify 5 稳定兼容版；JSON Schema + 兼容的 TypeBox type provider；@fastify/swagger 生成 OpenAPI。固定依赖版本，验证插件兼容矩阵。
- PostgreSQL 驱动 node-postgres（pg）；数据访问使用稳定版 Drizzle ORM 和可审查的 SQL migrations。不要因为某个教程使用 @rc 就安装预发布版本。复杂事务、锁、索引与查询可以使用参数化 SQL。
- BullMQ + ioredis。独立后端中 `api-server`、`worker`、`admin`、`scheduler` 是四个容器角色，不是四套重复业务代码；可共用镜像与领域服务。
- 测试使用 Vitest 与 Fastify inject；数据库/队列集成测试使用真实的临时 PostgreSQL、Redis，不用 SQLite 或内存 Map 冒充。
- Docker Compose：正式开发/验收基线为同一 `compose.yaml` 中的 api-server、worker、admin、scheduler、postgres、redis 和一次性 migrate。宿主单进程调试只是可选便利，不能替代独立容器验收。日志用 Fastify/Pino，其他观测先最小实现。
- admin 独立管理 API，默认补最小运营网页，可用 Fastify＋自动转义的轻量服务端模板；这是本包对未指定管理端 UI 栈的默认建议，不新建 React/Vue SPA 或第二套业务后端。
- 文件存储：开发先使用受控持久卷 LocalStorageAdapter，不强制再安装一套存储集群。实现 StoragePort，后续/发布前按部署方案启用一个真实对象存储适配器；S3-compatible 与厂商专有 API 分开验证。

只引入当前阶段实际需要的包。首期不引入 Kafka、Kubernetes、微服务治理、GraphRAG、独立向量库、模型训练集群或第二套 Agent 框架。

## 二、产品硬边界

1. 产品服务创作者：录音卡/资料导入 → 整理成个人资产 → 标签分类和查找 → AI 讨论与创作 → 保存成果。
2. 当前日常录音采集来自录音卡。蓝牙/Wi-Fi连接、卡内文件传输主要由手机和硬件完成；后端负责设备归属、云端资源、上传、转写和后处理。不能设计一个云 HTTP API 并宣称可直接控制未联网蓝牙硬件。未来手机录音只保留数据来源扩展口，不新增 UI。声纹登记、聊天语音输入另按当前 App 实际协议判断。
3. 标签先做：原文先保存，允许用户管理标签，系统提取上限默认5个、通常3—5个，无合适标签可以少于3个，不强凑。标签提取是异步可失败步骤，不影响原文读取；失败和示例输出不得冒充真实 AI 结果。
4. 检索首期是已授权资产内的关键词、正文、标签、时间与来源查询。预留 SearchPort，但不安装 pgvector、不调用 Embedding/Rerank、不采购云知识库。后续同样不自行增加语义/向量知识库。图片/视频/附件可以存储或提供给明确支持的工作流，不等于建立它们的语义索引。
5. 图谱与列表、资产使用同一份内容身份。后端只返回有依据的主题聚合、节点和局部边，不负责3D渲染，不将装饰网格伪造成语义关系。
6. 继续使用用户的 Dify 工作流思路：后端调用 Dify；工作流插件调用本服务受控工具 API 读取素材、数字孪生。不要因历史仓库名称改用 Coze，不重写用户全部工作流。
7. 数字孪生始终叫“数字孪生”，保留原UI及“数字形象/文件”等组织方式。三个固定维度：个人背景与经历、观点与方法、语言与表达。正文用 Markdown，小条目和轻量修订即可。系统只生成候选；用户确认才生效；支持手动编辑、删除、来源。没有周期自动学习、自动训练或无人确认的正式档案改写。
8. 支付订单、会员权益、额度用量分别负责。用户没有确定价格/额度/收费政策，不得从历史代码白名单或示例值擅自制定正式商业规则。开发 fixture 明确隔离，正式启用需已配置的版本化政策。
9. 外部世界需要栏目/资讯接入、关注、阅读、保存副本和选题素材；不建公开社区、团队协作、课程商城或任意网站无边界爬虫。
10. 代表作及专属章节不进入本期新建范围，不偷偷改名后重建；通用创作、草稿和历史保留。历史数据不擅自删除。桌面端不在当前项目验收范围。
11. 本项目是后端实施，不修改 Figma、不换 App 配色、不改名产品。必要的 App API/Repository 适配逐项登记且保持最小；改动 App 工作区需单独授权。

## 三、架构与边界

采用**独立于 huahuo-app 的一个后端代码库**，模块化业务、分角色容器部署。Fastify 分别构建 `buildApiServer()` 和 `buildAdminServer()`，管理路由不装载到公共 API。按业务域使用 Fastify plugin 注册路由；routes/schema/service/repository 按需要分层，不为每个简单CRUD强造多层抽象，也不建立能操作所有表的通用 repository。

建议目录：

```text
src/
  apps/{api-server,admin}.ts      # 分别build，支持inject，导入无监听副作用
  entrypoints/{api-server,worker,admin,scheduler,migrate}.ts
  config/
  plugins/                       # DB、Redis、auth、OpenAPI、error、logging
  modules/
    identity/  workspaces/  devices/  storage/
    assets/  search/  recordings/  conversations/
    ai-runtime/  creation/  digital-twin/  discovery/
    billing/  membership/  usage/
    notifications/  support/  admin/  tasks/
  integrations/                  # Dify、ASR、SMS、payment、storage、push
  admin-ui/                      # 管理网页模板/静态资源，只由admin装载
  contracts/                     # 公共DTO、schema和App兼容serializer
  shared/                        # 少量通用错误、时间、ID、分页；不塞业务
migrations/
tests/{unit,integration,contract,e2e}/
scripts/
infra/
compose.yaml                     # 所有角色同一Compose；PG可用profile停用
docs/{adr,contracts,runbooks}/
```

- PostgreSQL 是用户、内容、订单、权益、账本、任务、最终结果的权威存储。
- Redis 不是唯一任务账本、会员账本或持久会话历史；不要认为开启AOF就免除恢复设计。
- 音频、图片和大文件不作为大块 Base64 存入 PostgreSQL/Redis；DB保存资源身份和元数据。
- Run、任务、支付流水、数字孪生条目的生命周期独立，不统一成一个随意更新的 status 字段。
- 外部调用在数据库事务外执行；短事务记录意图、身份、结果和本地原子副作用。
- api-server/worker/admin/scheduler复用业务服务，但必须为独立容器；worker不是HTTP回调里的无持久化Promise，admin也不是api-server内部的隐藏路由分组。
- admin 仅提供管理页/管理API；耗时动作写task/outbox，由worker执行。scheduler投递和扫描，不执行付费模型/转写/退款任务本体。
- Docker构建上下文只包含后端；App checkout不复制、不挂载到业务容器，不做运行时git clone。每角色最小配置与数据库权限；迁移凭据只传migrate。

## 四、必须从第一天遵守的实现规则

### 契约
- 默认 API 前缀 /api/v1。与 App 已消费接口重合时按实际请求与解析核对路径、鉴权头、枚举、响应包装、幂等头、ETag和流式协议；不要简单把所有响应都改成一种格式。
- CODE（代码已核实）、USER（用户要求）、PROPOSED（本方案默认）、BLOCKED（待资料）分开登记。本提示词中的目录和新增API是建议，不是对现有App实现的声明。
- **每阶段固定核对 App： https://github.com/kyriswu/huahuo-app 。** 按 `07_App代码持续参照与契约核对.md` 记录 commit、实际路径/符号/行号、请求/响应解析、夹具及测试；不能只在P01/P15看一次。阶段内锁定本机已读文件基线，阶段间检查本机差异；不自动联网/fetch/pull/覆盖工作树。
- 每阶段只补本模块契约，不重复全仓审计。源码不可访问时继续独立服务开发，将兼容项标为UNVERIFIED_APP；不得编造已读代码、不得宣布契约通过。App已有返回不能直接照搬成新的商业规则，冲突要登记决策。
- Fastify请求及响应schema、OpenAPI、DTO、集成测试保持一致；不要接受用户输入或LLM输出作为可执行schema。数据库鉴权放在明确钩子/服务中，不放进schema编译逻辑。
- 任务受理后返回稳定task/run身份；客户端断开不自动等于取消云任务。任务成功必须能读取已提交的结果。

### 安全与作用范围
- userId来自认证，workspaceId必须验证访问权。管理员使用独立身份、Session/issuer/audience和RBAC，普通用户JWT不得作为管理员登录；管理台Cookie、CSRF和审计与App鉴权分别设计。所有资产/附件/搜索/任务/缓存/工具API都执行同等隔离；跨域引用需要显式授权，不把全局ID当授权凭证。
- 默认个人工作区，当前内容线与Workspace关系从App核对后作一次ADR确定，不建两套互不相通的工作区模型，也不扩展团队UI。
- JWT/Session、刷新令牌、短信验证码有失效与撤销；令牌和验证码哈希存储，日志不输出正文/密钥/购买凭据/带签名完整URL。开发登录绕过必须双重显式开发配置，生产无法启用。
- Dify工具凭证短期、限定任务和scope，权限由服务器派生；不能让模型提供userId、任意SQL、存储路径或任意URL来取得数据。
- URL导入和外部采集有SSRF防护：限制协议、拒绝私网/回环/link-local/云元数据、重定向逐跳复核，防DNS重绑定，限制下载量/超时/压缩展开，生产使用可约束出站网络。内部provider endpoint由可信配置单独控制。
- Markdown/HTML/转写和网页都是不可信内容。保留原文与来源，显示需安全处理，模型内容不能改变工具权限。

### 数据一致性
- 正式写入采用业务事务、唯一约束和版本检查。金额用最小币种单位整数；额度有明确单位，内部不使用浮点结算；超出JS安全整数范围用明确的字符串协议/安全转换。
- 日期存UTC，区分录制/导入/发布/更新时间，日历按用户时区归属。
- 创建型操作的幂等记录持久化到PG：scope+operation+key+requestHash，重复请求重放结果，同key不同请求409。已有App两种幂等头按端点兼容；同时传入冲突值时拒绝，不静默选一个。
- 任务受理：同事务写业务意图、task、outbox；投递可重试，重复投递不得重复业务效果。不宣称跨外部服务全局exactly-once。
- 只在可信支付事实、正式结果持久化等条件成立后更新权益/结果；来源删除、失效及版本冲突不能被异步迟到结果覆盖。

### Worker、Redis和降级
- BullMQ队列至少区分内容/语音、AI、商业化、通知维护，分别设置有上限的并发和重试，单个Worker进程可处理多队列，不强制每队列独立容器。
- Redis用于BullMQ时配置AOF、持久卷及noeviction。初期缓存和队列允许共用一实例，但缓存TTL和内存预算明确；DB编号/前缀不是内存隔离。配置REDIS_CACHE_URL和REDIS_QUEUE_URL，默认相同，后期可拆实例。
- API生产者快速失败/受理为等待投递的行为明确；Worker可重连。Redis不可用时，PG已持久化任务可显示等待投递；在PG和outbox都没写成功时不能返回已受理。
- Outbox确认投递后仍可能遇到Redis恢复/清空；实现从PG未完成任务对账与安全再投递。已产生外部身份或未知提交结果时先查询，不盲目重跑付费请求。
- 重复/迟到worker通过任务attempt/version检查和结果唯一约束防止覆盖；外部调用超时保存unknown/reconciling，供应商不支持查询时等待明确处置。
- 商业/AI/SMS限流与鉴权失效时保守拒绝，不因Redis故障放开无限费用；普通只读数据可以按明确策略降级。
- Scheduler是独立容器，只在该入口登记/扫描调度；不等于旧的BullMQ QueueScheduler类。使用已选版本受支持的调度接口；调度配置/去重窗口可恢复，重启不得重复发会员。

### 模型、支付和外部服务
- SmsProvider、StoragePort、AsrProvider、WorkflowProvider、PaymentProvider、PushProvider按接口适配，不在业务层散落SDK调用。
- 开发可用确定性模拟服务，并保存providerMode与测试身份。不能在生产缺密钥时自动返回虚构转写、虚构标签、假支付成功、假推送送达。
- 单模块无真实凭证时完成适配代码、故障fixture和配置校验，状态标记“模拟验证/待sandbox/待live”，继续其他模块；不能把全项目卡住，也不能说已上线。
- 只有启用的生产功能才要求相应真实配置；禁用功能明确返回能力未配置。生产模式禁止选择模拟付款、模拟用户身份和模拟供应商成功。
- 支付优先按官方SDK/文档，当前规则实施时核对。客户端SDK成功不直接发权益；通知验签后先持久化再按通道ACK，不能一律套JSON响应包装。
- 不擅自触发真支付/退款/短信/付费模型/云迁移/生产部署。真实沙箱与生产验证分别需用户配置和授权。

第一阶段就在用户现有huahuo-server实施。先检查内部与隐藏文件；确实为空则初始化，有内容则保护并增量补齐。发现与所述空目录不符的已有业务先说明，不能清空、擅自迁移旧Express或另外新建项目。

本机实施和验证范围按11/12规范：仅操作huahuo-server和本项目Compose资源，不修改App，不在ChatGPT运行环境假称启动了用户Mac。

阶段完成后用短回复报告：已实现/已测试/模拟验证/外部阻塞/下一步。用户说“继续下一阶段”时读取progress接着做，不重新搭脚手架。每阶段可分小提交，但不擅自push、发布或删除数据。

“完整”意味着产品范围、真实契约、数据库持久化、Worker恢复、计费一致性、权限、安全和部署流程均有可核对结果，不是所有endpoint返回200，也不是拥有很多空目录。
