# 架构与配置约定 · v3

持续约束：执行前阅读 [知识图谱标签化补充要求](13_知识图谱标签化补充要求.md)；图谱只做标签驱动的素材关联，后续也不得自行增加向量/RAG/Dify 知识库。与旧条款冲突时以该补充要求为准。

本文件中的新增工程选择是实施规格，不是已经运行的源码。业务范围沿用此前完整阶段，部署延续v2；目录与App参照按v3固定为本机huahuo-server／../huahuo-app。

前端只读参照：https://github.com/kyriswu/huahuo-app。独立后端不放入该仓库，App不进入镜像/运行依赖。

## 1. 最小部署形态：同一Compose，独立容器

```text
Flutter App（单独仓库） ───────→ api-server :3000
管理员浏览器（私网/回环） ───→ admin :3001
Dify工具／供应商可信回调 ────→ api-server的限定入口
                                  │
            ┌─────────────────────┴───────────────┐
            │  PostgreSQL：正式数据／task／outbox   │
            └───────────────┬─────────────────────┘
                            │
             scheduler：调度、Outbox投递、补偿扫描
                            │
                   Redis／BullMQ 队列
                            │
                       worker：执行
                            │
        Dify／ASR／解析／标签／付款核验／通知 → 正式结果回PG

migrate：一次性连接所选PG，角色准备/迁移成功后退出
postgres：local-db profile（云PG模式不启动）
redis：本地持久容器，缓存和队列分前缀/配置，可后续拆实例
```

共享一个后端代码库、同一镜像可复用；四个角色不同entrypoint，不注册不属于本角色的路由、消费者或周期扫描。API/管理台不因彼此重启而停机；worker退出不会导致HTTP进程退出。没有HTTP流量时scheduler照常投递，worker照常消费。

## 2. PostgreSQL配置与角色

只通过配置连接；本地PG位于 `local-db` profile，云PG模式不启用这个profile。**api-server/admin/worker/scheduler/migrate 不直接depends_on postgres**，否则切云时会引用被禁用服务。migrate对实际endpoint做有截止时间的重试，常驻服务依赖migrate成功并验证schema版本。

容器使用 `postgres:5432`、`redis:6379`，不能用localhost指代另一容器。宿主运行时使用单独配置；后端业务镜像不能读取宿主App绝对路径。

推荐变量（按角色显式注入，不把整份.env传给所有服务）：

| 配置 | 责任 |
|---|---|
| DATABASE_API_URL / DATABASE_ADMIN_URL / DATABASE_WORKER_URL / DATABASE_SCHEDULER_URL | 每个运行角色的连接，在容器内映射为DATABASE_URL；生产非superuser，权限按业务最小化 |
| DATABASE_MIGRATION_URL | 专用迁移连接，只给migrate；云PG不要求拥有无法授予的superuser权限 |
| DATABASE_SSL_MODE / DATABASE_SSL_CA_FILE | local可disable，云PG验证证书与主机名；连接串ssl参数冲突需拒绝或统一解析 |
| DATABASE_POOL_MAX_* | 每角色池预算，扩worker副本时累计核算，不按单进程值想象全站连接量 |
| REDIS_CACHE_URL / REDIS_QUEUE_URL | 默认同一Redis容器的不同逻辑DB；不是内存隔离 |
| APP_PUBLIC_BASE_URL | Flutter/外部provider能访问的API地址，不等于Docker内部服务名 |
| INTERNAL_API_BASE_URL | 同机网络内可信调用地址；不要返回给手机或云Dify |
| ADMIN_PUBLIC_BASE_URL / ADMIN_SESSION_SECRET | 管理端独立地址、密钥与cookie域 |
| APP_ENV / PROVIDER_MODE | 模拟与真实环境边界，与Node构建优化的NODE_ENV分别处理 |

migrate在初次本地空库创建非superuser角色，可通过受控init脚本准备；常驻角色不得使用初始化owner。云PG角色由云权限范围内管理员预先建立；环境无权建角色时明确列出人工步骤，不能退化成全员superuser。

`.env.compose.local.example` 与 `.env.compose.cloud.example` 使用同一compose.yaml；实际凭据本地生成、忽略提交。具体版本/digest在P01锁定，模板不是可直接上线的秘密配置。

切endpoint只改连接目标，不移动现存数据。另行处理数据迁移、TLS、网络、角色、扩展、migration及回归。不要`rejectUnauthorized:false`长期关闭验证；node-postgres的连接串SSL参数可能覆盖独立ssl对象，配置层必须做冲突测试。

迁移一个release job执行，持有项目级迁移锁，完成即退出；既有API/worker/admin启动不自动迁移。后续发布通过受控命令明确执行migrate，不假定上次已退出0的容器能证明新版本迁移完成。

## 3. Redis 的两种责任

起步一台容器可共用，但不能把队列实例配置成随时LRU驱逐的普通缓存。推荐：AOF开启、appendfsync按选定部署策略、持久卷、noeviction、最大内存和告警。队列/缓存使用不同前缀与逻辑DB只能降低误操作，不是资源隔离。

缓存有TTL、条目大小及总预算。队列数据只放taskId/必要的非敏感字段，不把原文、音频Base64和永久凭证塞入Redis。支付、余额、任务终态从PG读取或校核。

缓存失效的允许结果是慢一些，不能变成越权或错误权益。队列丢失通过PG安全对账；任务已外部提交时须核对外部身份，不能直接恢复成“尚未执行”。

## 4. 两个可靠事务边界

### 业务写入与任务投递

短事务写业务记录、task、outbox；dispatcher短事务领取outbox并释放数据库事务，在外部投递BullMQ，成功后标dispatch。重复发送同一业务task不得重复产生业务结果。PG任务对账负责补救“已标dispatch但Redis数据丢失”。

任务与业务结果唯一键是真实去重依据，不能只依靠BullMQ jobId（作业清理后可能再次出现）。重试生成与任务attempt有清楚关系；外部副作用可能发生时保持unknown并优先查证。

### 支付与权益

验签/渠道查询取得可信事实 → inbox持久化 → 商业Worker处理 → 支付事实、权益来源和额度授予在PG受控事务更新。

支付状态与会员状态分离；订单支付成功但发权益失败是可补偿状态，不是再次收费。相同交易/通知/订阅周期/授权批次必须有唯一约束。退款通过冲正/撤回相应来源处理，不修改旧账目“伪装从未发生”。

## 5. 任务、运行与事件

Task可表达 queued、running、waiting_external、retry_scheduled、reconciling、succeeded、failed、cancel_requested、cancelled；具体枚举与App协议映射，不能直接将本枚举冒充App的原状态。

Run额外记录workflow/profile、provider run identity、context snapshot、用户输入/输出、usage与result reference。子任务完成不自动表示整个Run可读取；先保存结果再发布成功事件。

SSE使用稳定runId+单调序号，事件先经过持久化缓冲再发布。合并token小片段，避免每个token独立写库；断线用游标重放，超出留存窗口返回快照恢复指示。数据量/连接数/心跳/背压有上限，不把Redis Pub/Sub当历史。

事件中只包含面向用户的阶段和内容，不暴露模型私有推理、供应商密钥或任意内部堆栈。

## 6. 云端文件与用户空间

资源拥有者与workspace关系明确，保存storage driver/bucket/key/object version等稳定定位。临时签名URL不作为主键或永久消息内容，重新打开历史时重新授权生成。

开发LocalStorageAdapter：路径由后端生成，不能接受客户端文件系统路径；api-server与worker挂同一持久卷；admin/scheduler默认不挂用户文件卷；上传以stream写临时文件并限制大小，核验后原子落位。下载走授权Resource ID路由，支持音频Range，防目录穿越、软链接越界、覆盖攻击。

正式对象存储：按选定厂商的接口支持直传/分段与complete校验，不能假设所有云都完全兼容S3。资源未核验不能被ASR或Dify读取。存储预留量/已使用量单独计量，失败上传释放预留，复制引用不重复计物理字节的规则写清。

## 7. 扩展能力的顺序

已定：PG、Redis、Fastify。
本方案补齐：TS、Drizzle/pg、BullMQ、OpenAPI、测试、文件适配。
待供应商资料：短信、ASR、支付商户、存储、推送、Dify应用配置。
禁止自行引入向量检索、Rerank、GraphRAG；通用 Agent 平台、微服务/K8s 不在当前范围。

供应商资料缺失不是伪造成功的理由，也不阻止先完成业务事务、HTTP契约、模拟故障和可运行骨架。

## 9. 本机双目录约束

Server的绝对路径由Codex当前目录定位，不写死用户名；App默认../huahuo-app只作宿主参照。compose.yaml/build.context `.` 的语义必须是Server根。配置的APP_LOCAL_PATH不注入业务容器。

本机环境先检查Docker和Node是否可用；使用精确镜像的tooling target是主机缺Node时的可选实现方式，不增加第二套后端。开发PG/Redis和用户文件使用命名卷，不写进源码目录或App。已有凭据和project卷不能每次“初始化”重置。

见11规范的已安装Docker启动授权边界与12规范的真机/模拟器/回调地址。保留本地PG/云PG一份Compose，不为本机源码参照创建额外App容器。
